# IBVAP AI Service — Phase Design

**Status:** Initial implementation baseline; production validation pending  
**Phase:** AI video analytics service  
**Purpose:** Document the implemented service baseline, its interfaces, and the gates for production deployment.

## 1. Objective

Build a separately deployable Python service that turns standard IP-camera video streams into structured detections, tracks, and security events. It is the computer-vision component of IBVAP; it does not replace the existing CCTV cameras or take responsibility for the command-and-control user interface.

The service must support CPU-only deployments and allow GPU acceleration where available. Processing must be configurable per camera so the same service can be deployed at a remote site or scaled centrally.

## 2. Proposed technology stack

| Concern | Proposed technology | Notes |
| --- | --- | --- |
| Service/API | Python and FastAPI | Versioned REST endpoints; OpenAPI schema generated by FastAPI. |
| Video decoding | FFmpeg, with OpenCV for frame handling | Support standard RTSP streams first. Keep decoding behind an adapter so alternatives can be added. |
| Frame processing | OpenCV and NumPy | Resize, color conversion, image handling, and geometric zone checks. |
| Object detection | YOLOv8 ONNX detector adapter | Detect people and supported vehicle classes using the documented raw-output layout; compatible weights are external and must be licensed. |
| Multi-object tracking | ByteTrack via Supervision | Per-camera object association; IDs are transient and not identities. |
| Face detection | OpenCV Haar cascade baseline | Detection only; no identity matching. Replace only after license and representative-footage evaluation. |
| Plate detection and OCR | One-class YOLOv8 ONNX plate detector plus Tesseract OCR | OCR is local and confidence-filtered; jurisdiction-specific accuracy remains to be evaluated. |
| Persistence/integration | SQLite event log and polling API | 30-day configurable default retention; event push/C2 integration is not implemented in this phase baseline. |
| Packaging | Docker-compatible service | The provided image uses CPU ONNX Runtime; GPU deployment requires an image with the compatible GPU runtime/provider and host drivers. |

**Model and dependency licensing is a release gate.** Before selecting or distributing model weights or inference packages, record their licenses and confirm that they permit the intended government, commercial, and on-premises deployment. Do not bundle weights until this review is complete.

## 3. Phase scope

### Included

- Ingest configured RTSP camera streams and process frames continuously.
- Detect people and vehicles, classify supported vehicle types, and track detections across frames.
- Detect faces without determining a person's identity.
- Detect vehicle license plates and return OCR text with confidence and source-camera/time metadata.
- Evaluate configurable virtual-fence zones and generate intrusion events when tracked objects cross into restricted zones.
- Generate initial rule-based suspicious-activity events from explicit, configurable rules (for example, loitering duration or restricted-zone entry). Avoid claiming general intent or behavior understanding.
- Support a configurable night-movement event mode; accuracy evaluation on day/night and IR footage remains a rollout gate.
- Emit structured, timestamped events and expose service health and camera-processing status.
- Persist events to SQLite with configurable retention, expose event polling, and allow a local development/test mode using video files.
- Provide a local image-analysis demo route and browser page for illustrating single-image detections without retaining the uploaded image.

### Not included in this phase

- Face recognition, identity matching, watchlists, or biometric search.
- Automatic decisions to engage, detain, or identify a person. Alerts are advisory and require human review.
- A command-center UI, camera provisioning UI, long-term evidence archive, or incident case-management workflow.
- Training custom models or promising performance on footage that has not been evaluated.
- Replacing camera firmware, NVRs, or other existing CCTV infrastructure.
- Outbound event push/C2 integration and persistent camera-configuration storage.

## 4. Service architecture

```text
IP camera (RTSP) / test video
          |
          v
Stream reader (FFmpeg/OpenCV; reconnect and health state)
          |
          v
Frame sampler and preprocessor
          |
          v
Detector (person, vehicle, face, plate)
          |
          +----> Plate OCR adapter
          |
          v
Tracker (ByteTrack; per-camera track IDs)
          |
          v
Rule evaluators (virtual fence, loitering, night movement)
          |
          v
Event normalizer ---> SQLite event log ---> polling API ---> platform/C2 integration
          |
          +----> metrics and camera processing status

FastAPI control plane: camera configuration, status, health, and event queries
```

The stream-processing loop must not be tied to the lifetime of an HTTP request. The API configures and observes processing; a managed worker owns each active camera pipeline. Each camera has isolated stream, tracker, and rule state. Camera configuration is in memory and must be registered again after service restart. A camera disconnect updates its status and triggers bounded-interval reconnect attempts without stopping other cameras.

## 5. Initial API contract

All endpoints are under `/api/v1`. Exact authentication and event delivery mechanism are platform integration decisions; production deployment must not expose unauthenticated camera or event controls.

In the implementation baseline, all `/api/v1` routes require a configured `IBVAP_API_TOKEN` sent using the `X-API-Key` header. `/health` and `/ready` are unauthenticated health endpoints and must still be network-restricted in deployment.

| Method and path | Purpose |
| --- | --- |
| `GET /health` | Liveness check for the API process. |
| `GET /ready` | Readiness check, including whether required models and runtime are available. |
| `POST /api/v1/cameras` | Register a camera configuration and optionally start processing. |
| `GET /api/v1/cameras` | List camera IDs and non-secret processing status. |
| `GET /api/v1/cameras/{camera_id}` | Read configuration metadata and current status; never return stream credentials. |
| `PATCH /api/v1/cameras/{camera_id}` | Update analytics settings or zone configuration. |
| `POST /api/v1/cameras/{camera_id}/start` | Start or resume that camera's pipeline. |
| `POST /api/v1/cameras/{camera_id}/stop` | Stop that camera's pipeline. |
| `GET /api/v1/events` | Query recent events using camera, type, and time filters. |
| `POST /api/v1/images/analyze` | Analyze one uploaded image using selected image-capable analytics; do not persist the image or create an event. |

The browser showcase is served at `/`. It is intended for local demonstrations, not as a replacement for a command-center UI. Compatible model weights remain external, and the upload route cannot establish tracking, loitering, live-stream behavior, or production accuracy.

An initial camera configuration includes `camera_id`, stream URL, enabled analytics, processing frame rate, optional polygons/zones, and any rule thresholds. Credentials must be supplied through protected deployment configuration, not logged or returned by the API. Prefer RTSPS where supported.

Example event payload:

```json
{
  "event_id": "generated-unique-id",
  "event_type": "virtual_fence_intrusion",
  "occurred_at": "2026-01-01T12:00:00Z",
  "camera_id": "bop-gate-01",
  "track_id": "camera-scoped-track-id",
  "object": {
    "class_name": "person",
    "confidence": 0.94,
    "bounding_box": {
      "x": 0.21,
      "y": 0.18,
      "width": 0.13,
      "height": 0.46
    }
  },
  "zone_id": "restricted-area",
  "evidence": {
    "snapshot_reference": null
  }
}
```

Bounding-box coordinates are normalized to `[0, 1]` relative to the source frame. Event timestamps are UTC. Events should include the detector/rule confidence where meaningful, but must not imply certainty beyond the underlying signal. The service retains event records in SQLite for 30 days by default (configurable); it does not store video or snapshots.

## 6. Analytics behavior

### Detection and tracking

- Person/vehicle inference uses raw YOLOv8 ONNX output in the standard 80-class COCO layout; the plate model uses a one-class raw YOLOv8 ONNX output. Model weights are external and are not bundled.
- ByteTrack is used for per-camera track association. IDs are transient and are not person identities.
- Current face detection uses OpenCV Haar cascade and does not provide a calibrated confidence score; it is a baseline, not a production accuracy claim.
- Use configurable confidence and non-maximum suppression thresholds, with documented defaults.
- The person/vehicle detector retains low-confidence candidates for ByteTrack association; detections below the configured confidence threshold do not emit events or trigger rules.
- Keep class labels limited to classes the selected model can reliably distinguish.
- Allow frame sampling to trade off inference cost and alert latency. Record the effective sampling rate.

### ANPR

- Run plate OCR only on detected vehicle/plate regions rather than full frames.
- Run local Tesseract OCR and return the recognized string, OCR confidence, plate bounding box, and timestamp only when confidence meets the configured floor; do not treat text as verified identity.
- Normalize text only according to a documented, region-specific policy. Preserve the raw OCR result for review if the platform's retention policy permits it.
- Validate against day/night, motion blur, oblique angles, occlusion, and supported plate formats before enabling production alerts.

### Virtual fence and activity rules

- Represent a zone as a named polygon in normalized frame coordinates.
- Define intrusion as a tracked object's bounding-box center crossing into a restricted polygon; boundary points count as inside.
- Define loitering through a configurable duration (zone override or service default) and zone, with duplicate-event suppression/cooldown.
- Treat night movement as a configured time window and/or camera mode plus person/vehicle detection. Do not claim reliable night detection without testing the site's visible-light/IR imagery.
- Keep rules deterministic, reviewable, and configurable. Do not label a person or action as suspicious without an explicit rule that produced that event.

## 7. Reliability, performance, and deployment

- A camera pipeline failure is isolated: it must not terminate processing for other cameras.
- Report per-camera states such as `stopped`, `connecting`, `running`, and `error`, plus last-frame time and a sanitized error category.
- Bound stream reconnect frequency and inference queues. Prefer dropping stale frames over building unbounded latency.
- Keep inference configuration (device, model paths, thresholds, and sampling rate) external to source code.
- Expose per-camera stream state and last-frame time, log sanitized worker errors, and avoid logging credentials, raw frames, or plate text. Event-rate metrics are not implemented yet.
- Expose per-camera processed/dropped-frame counts and inference timing through an authenticated metrics endpoint. Event-rate metrics remain a future integration concern.
- Do not claim a camera count or frame rate until benchmarks are run on the target CPU/GPU, stream resolution, and selected models.
- Record hardware, model/version, resolution, sampling rate, and dataset conditions with each benchmark.

## 8. Privacy, security, and operational safeguards

- Face detection is distinct from face recognition; no face embeddings, identity database, or matching endpoint is in scope.
- Treat plate text, snapshots, and event metadata as sensitive operational data. Apply least-privilege access, encrypted transport, and the platform's access/retention policy.
- Redact stream credentials from logs, errors, API responses, and metrics.
- Restrict camera and event endpoints to authorized callers in production; document network boundaries and secret provisioning before deployment.
- Keep event delivery retry-safe using stable event IDs and define duplicate handling at the sink.
- The current baseline persists events to SQLite and exposes polling; reliable event push/retry delivery remains a platform-integration task.
- Surface model and stream errors explicitly. Do not convert a failed inference or unavailable camera into a normal/no-detection result.
- Alerts support human situational awareness and require operator assessment.

## 9. Verification and acceptance criteria

Before production rollout, the phase should demonstrate:

1. Unit tests for input validation, zone geometry/boundary cases, event construction, rule thresholds, and duplicate suppression.
2. API tests for camera lifecycle, health/readiness, validation errors, and secret redaction.
3. Pipeline tests against short, licensed test clips for people/vehicle detection, tracking continuity, plate OCR output shape, and event generation.
4. Failure tests for unavailable RTSP streams, reconnect behavior, malformed configuration, and model-load/inference errors.
5. Measured precision/recall or task-specific accuracy for each enabled analytics capability on representative, labeled footage. Report dataset conditions and limitations; agree on numeric go-live targets after a baseline evaluation.
6. A load/latency benchmark on the intended deployment hardware, including multiple cameras and the configured frame-sampling rate.
7. A deployment smoke test with a standard IP camera or an RTSP-compatible test source.
8. A documented model/dependency license review and privacy/retention approval before production rollout.

## 10. Decisions to confirm before implementation

- Initial deployment target: CPU-only edge server, GPU-equipped edge server, or central GPU server.
- Number of simultaneous cameras, typical resolution, and acceptable alert latency.
- Supported plate jurisdictions/formats and acceptable OCR confidence/accuracy.
- Which authorized push mechanism (webhook/message broker) to add beyond the current polling API.
- Zone configuration ownership and whether polygons are defined in this service or supplied by another platform component.
- Storage, access, and retention rules for snapshots, event metadata, and plate text.
- The exact detector, tracker, OCR engine, model weights, and their licenses.
- Numeric acceptance targets for each capability after representative test footage is available.

The software baseline is implemented with the documented CPU-first defaults, API, local image showcase, and a reproducible local-video demo path using an externally downloaded Ultralytics YOLOv8 asset. That asset remains subject to its own license and is not bundled. Representative validation media, target-hardware benchmarks, plate-model validation, and production integration decisions remain open; do not treat demo output as production-validated.
